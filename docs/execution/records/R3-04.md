## Evidence brief before implementation

- Current behavior:
  - R3-01 defined the shared typed analysis operations on the server.
  - R3-02 exposed these operations to VS Code language model tools via `AnalysisToolService`.
  - Currently, external non-VS Code clients (e.g. standalone agents, Claude Desktop, Cursor, external tools) cannot access these analysis operations because there is no MCP adapter.
- Failure/missing behavior and smallest reproducer:
  - Missing MCP adapter: External clients cannot discover tools (`tools/list`) or execute analysis reads (`tools/call`) over the standard Model Context Protocol.
  - Missing disk-facts labeling: External clients might erroneously assume they see unsaved in-memory editor buffers unless explicitly declared.
  - Missing boundary validation for external transport: Malformed JSON-RPC calls or expired pagination cursors must be safely rejected with standard MCP / JSON-RPC error codes.
- Relevant invariant IDs and affected owner/reader/cache boundaries:
  - `INV-TOOL-001`: Shared analysis boundary — MCP adapter must reuse the same typed analysis operations without creating a secondary index or duplicate project models.
  - `INV-TOOL-002`: Read calls do not execute builds or applications implicitly.
  - `INV-TOOL-003`: Boundary validation for trust, scope, pagination, and payload limits independent of MCP annotations.
- Unknowns and how this task will resolve them:
  - Standard JSON-RPC 2.0 framing for MCP: Implement standard stdio message parsing (supporting newline-delimited JSON and Content-Length framing).
  - Session lifecycle: Handle `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`, `notifications/cancelled`, and EOF/disconnect cleanup.

## Implementation decision

- Intended observable result; non-goals:
  - Observable result:
    1. `GrailsMcpServer` implementing standard MCP JSON-RPC 2.0 protocol over any readable/writable streams (stdio or duplex).
    2. Exposes 4 tools: `grails_project_capabilities`, `grails_symbols_search`, `grails_symbols_explain`, `grails_project_diagnostics` matching the canonical schemas.
    3. Reuses the same typed backend analysis operations and error envelopes (`AnalysisErrorResponse`) without duplicating indexes.
    4. Labels responses with explicit `diskFacts` mode ("external clients operate on committed disk facts and do not implicitly see unsaved editor buffers").
    5. Enforces input validation, query bounds, payload capping, stale cursor rejection (`CURSOR_EXPIRED`), and request cancellation (`notifications/cancelled`).
    6. Handles clean disconnect / session termination without resource leakage.
    7. CLI executable entry point (`client/src/mcp/index.ts`) and unit test suite (`client/src/test/grailsMcpServer.unit.test.ts`).
  - Non-goals: Write operations, code edits, or mutations (owned by R5).
- Files/owners to change:
  - `client/src/mcp/GrailsMcpServer.ts` (New)
  - `client/src/mcp/index.ts` (New)
  - `client/src/test/grailsMcpServer.unit.test.ts` (New)
  - `package.json` (Update: add `"mcp:server"` script)
  - `client/STATUS.md` (Update)
  - `docs/execution/task-queue.json` (Update)
  - `docs/execution/records/R3-04.md` (This record)
- Input revision, candidate state, commit/publication and cancellation behavior:
  - External MCP client requests pass `requestId` and can be cancelled via `notifications/cancelled`.
- Cache/resource impact, limits and invalidation:
  - Output results are capped (max 200 symbol items, max 262,144 bytes). Disconnect frees all pending requests.
- Alternatives considered:
  - Direct Groovy MCP server: Rejected because TypeScript client already manages LSP connection and protocol JSON serialization cleanly.
- Contract conflict/ADR update, if any: None.
