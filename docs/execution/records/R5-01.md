## Evidence brief before implementation

- Current behavior:
  - Relationship modeling in R4-02 extracted typed edges across Grails artifacts, but did not project impact ripples when files or symbols are modified.
  - Agents lacked an operation to query downstream impact ripples without re-indexing the entire workspace.
  - Dynamic behaviors (GORM dynamic finders, wildcard URL mappings, reflection) were either guessed or omitted without explicit uncertainty disclosure.
- Failure/missing behavior and smallest reproducer:
  - Changing a domain class property could break controller actions or views without any warning to an agent assessing the scope of changes.
  - Cyclically dependent artifacts could trigger infinite traversal if cycles were not tracked.
- Relevant invariant IDs and affected owner/reader/cache boundaries:
  - `INV-DISC-003`: Declared APIs vs dynamic unknowns clearly distinguished.
  - `INV-TOOL-001`: Tool outputs identify exact input state (`analysisRevision: rev:<ver>:dep:<rev>`).
  - `INV-TOOL-003`: Bounded count/byte budgets, cycle termination, pagination cursors.

## Implementation decision

- Server implementation:
  - Models in `server/src/main/groovy/kingsk/grails/lsp/core/analysis/`:
    - `ChangeImpactItem`: artifactUri, artifactType, symbolKind, impactKind, confidence, reason.
    - `DynamicUnknownItem`: name, contextUri, reason, impactSurface.
    - `VerificationSuggestion`: testUri, testType, reason.
    - `ChangeImpactRequest`: projectUri, changedUris, depth, limit, cursor.
    - `ChangeImpactResponse`: schemaVersion, freshness, completeness, changedUris, impactedArtifacts, dynamicUnknowns, verificationSuggestions, cursor, limitations.
  - Service logic in `AnalysisOperationService.groovy`:
    - `executeChangeImpact`: validates request parameters, resolves project context, uses proven relationship edges, terminates cycles using a visited set, bounds traversal depth (default 2, clamped 1-5) and item limit (clamped 1-500), identifies dynamic unknowns (e.g. `findBy*` dynamic finders, wildcard URL patterns), attaches verification test suggestions, and issues pagination cursors.
    - Wired command in `GrailsWorkspaceService.groovy` under `grails.analysis.changeImpact`.
  - Spock tests: `GrailsChangeImpactSpec.groovy` with 3 acceptance specifications.
- Client implementation:
  - Types in `client/src/shared/protocol/analysis.ts` and `shared/schemas/analysis-operations.json`.
  - Service method `AnalysisToolService.getChangeImpact` with parameter bounding.
  - LM tool `grails_change_impact` and command `grails.analysis.changeImpact`.
  - MCP tool `grails_change_impact` in `GrailsMcpServer.ts`.
  - Unit tests: `changeImpact.unit.test.ts`.

## Implementation report

- Implemented features:
  - End-to-end change impact operation across server, client, LM tools, and MCP.
  - Proven relationship edge projection (domain -> controller, service -> controller, taglib -> view).
  - Explicit reporting of dynamic unknowns with reason and impact surface.
  - Verification suggestions suggesting test classes covering impacted artifacts.
  - Cycle-safe BFS traversal with bounded depth (1-5) and count limits (1-500).
