## Evidence brief before implementation

- Current behavior:
  - Standard LSP rename in `GrailsRenameProvider` provided single-pass workspace edits but did not support multi-step preview-before-apply flows required by agents and human reviewers.
  - Re-applying a rename against an edited buffer or obsolete snapshot risked silent data corruption or partial edits without version checks.
  - Dynamic references (e.g. dynamic GORM finders containing the renamed property) were either blindly renamed causing syntax errors or omitted silently without notice.
  - Existing member collisions (e.g. renaming a property to a name already present on the class) were not detected ahead of time.
- Failure/missing behavior and smallest reproducer:
  - If a file had modified unsaved editor buffers or bumped document versions, an agent rename could overwrite newer edits.
  - Dynamic finder invocations like `Book.findByTitle(query)` were ambiguous if `title` was renamed.
- Relevant invariant IDs and affected owner/reader/cache boundaries:
  - `INV-KEY-003`: Symbol identity coherence across references and declarations.
  - `INV-TOOL-002`: Previews/checks/application have explicit input identities, trust boundaries, and report honest results.
  - `INV-EDIT-001`: Workspace edit safety, version precondition validation, rejection of unmappable edits.

## Implementation decision

- Server implementation:
  - Models in `server/src/main/groovy/kingsk/grails/lsp/core/refactor/`:
    - `RenamePreviewRequest`: projectUri, documentUri, position, newName, options.
    - `RenamePreviewResponse`: schemaVersion, analysisRevision, canRename, oldName, newName, edits, collisions, uncertainMatches, limitations.
    - `RenameApplyRequest`: projectUri, expectedRevision, edits, options.
    - `RenameApplyResponse`: schemaVersion, success, appliedEditsCount, failures, recovered.
    - `RenameEditGroup`, `RenameEditItem`, `RenameCollisionItem`, `RenameUncertainMatch`.
  - Service methods in `AnalysisOperationService.groovy`:
    - `executeRenamePreview`: validates inputs and symbol resolution, captures file versions, detects collisions with existing members in enclosing scope, excludes uncertain dynamic matches (e.g. GORM dynamic finder patterns) while enumerating them in `uncertainMatches`, and formats edits with version preconditions.
    - `executeRenameApply`: verifies version preconditions against current snapshot and buffer state, rejects stale versions with clear recovery messages, and produces structured application results.
    - Wired commands in `GrailsWorkspaceService.groovy`: `grails.refactor.preview` and `grails.refactor.apply`.
- Client implementation:
  - Added `RefactorRenameService.ts` in `client/src/services/refactor/` registered in `ServiceContainer`.
  - Extended `AnalysisToolService.ts` with `getRenamePreview` and `applyRename`.
  - Registered `grails_refactor_preview` language model tool in `AnalysisToolService.ts` and `package.json`.
  - Registered `grails.refactor.preview` and `grails.refactor.apply` commands in `AnalysisCommands.ts`.
  - Unit tests in `client/src/test/renamePreview.unit.test.ts`.

## Implementation report

- Implemented features:
  - Multi-file preview generation with per-file edit grouping and document version preconditions.
  - Member collision detection warning when target name conflicts with existing properties or methods.
  - Dynamic GORM finder uncertain matches cleanly separated from definitive edits.
  - Application endpoint with precondition validation and honest rejection of stale generations.
  - Language model tool and editor command wiring.
