## Evidence brief before implementation

- Current behavior:
  - Prior to R5-03, the LSP server and client lacked a standardized, structured entry point for agents and tools to request bounded compile and test checks.
  - Tests were executed ad-hoc without formal input fingerprints linking results to specific snapshot revisions or dependency revisions.
  - No distinction was made between a suite with 0 matching tests (`no_tests`) and a passing suite, risking false confidence.
  - Narrow test passes were not explicitly qualified with limitations regarding whole-project pass status.
- Failure/missing behavior and smallest reproducer:
  - Without structured check execution, agents executing targeted tests cannot determine whether failure was caused by compilation errors, test assertion failures, or timeout/cancellation.
  - Running a narrow test class cannot be distinguished from a full-project validation without explicit scope metadata and disclaimer limitations.
- Relevant invariant IDs and affected owner/reader/cache boundaries:
  - `INV-TOOL-001`: Tool outputs identify exact input state (`analysisRevision: rev:<ver>:dep:<rev>`).
  - `INV-TOOL-002`: Previews/checks/application have explicit input identities, trust boundaries, and report honest results.
  - `INV-TOOL-003`: Distinguish success, failure, no_tests, skipped, and partial checks; bounded output.
  - `INV-PERF-002`: Process admission, bounded execution time (timeout clamped 1,000–300,000ms), and bounded output bytes (clamped 1,024–262,144 bytes).

## Implementation decision

- Server implementation:
  - Domain models in `server/src/main/groovy/kingsk/grails/lsp/core/check/`:
    - `CheckStatus`: `SUCCESS`, `FAILURE`, `CANCELLED`, `TIMEOUT`, `NO_TESTS`, `SKIPPED`, `PARTIAL`.
    - `CheckScope`: `projectUri`, `sourceSet`, `testClassNames`, `testMethodNames`, `extraTasks`.
    - `CheckDiagnosticItem`: `severity`, `message`, `uri`, `line`, `character`.
    - `CheckSummary`: `testsTotal`, `testsPassed`, `testsFailed`, `testsSkipped`, `compilationSuccess`, `errorCount`, `warningCount`.
    - `CheckExecutionRequest`: structured arguments with bounded timeouts and payload limits.
    - `CheckExecutionResponse`: complete execution record with schema version, status, duration, summary, diagnostics, output, artifact locations, and limitations.
  - Service logic in `AnalysisOperationService.groovy`:
    - `executeChecksRun`: enforces boundary argument validation, captures snapshot and dependency revision fingerprint, clamps timeouts (1s-300s) and output bytes (1KB-256KB), supports test/compile/all check types, detects compiler errors, distinguishes `NO_TESTS` from executed tests, and attaches narrow-test limitations when specific tests are run.
    - Wired command in `GrailsWorkspaceService.groovy` under `grails.checks.run`.
  - Spock tests: `GrailsChecksOperationSpec.groovy` covering 3 acceptance specifications.
- Client implementation:
  - Protocol & Schemas: Updated `shared/schemas/analysis-operations.json` and `client/src/shared/protocol/analysis.ts` with TypeScript interfaces for `CheckExecutionRequest` and `CheckExecutionResponse`.
  - Service: Added `runChecks` method with parameter bounds clamping and error validation in `AnalysisToolService.ts`.
  - LM Tools: Registered `grails_checks_run` language model tool in `AnalysisToolService.ts` and declared in `package.json`.
  - MCP: Added `grails_checks_run` tool handler with validation in `GrailsMcpServer.ts`.
  - Commands & UI: Added `RunChecksUseCase` and registered `grails.checks.run` in `AnalysisCommands.ts` and `package.json`.
  - Unit tests: Created `checksRun.unit.test.ts` verifying argument validation, bounds clamping, and MCP JSON-RPC protocol execution.

## Implementation report

- Implemented features:
  - Full end-to-end check runner across LSP, MCP, and VS Code LM tool interfaces.
  - Strict input validation rejecting invalid check types, missing URIs, and out-of-range bounds.
  - Reliable input fingerprinting via `analysisRevision` (`rev:<snapshotVersion>:dep:<depRevision>`).
  - Clear check status discrimination (`SUCCESS`, `FAILURE`, `NO_TESTS`, `SKIPPED`, `CANCELLED`, `TIMEOUT`, `PARTIAL`).
  - Output truncation respecting `maxOutputBytes` with truncation disclosure.
  - Narrow test disclaimer in `limitations` preventing unwarranted assumptions of full-project pass.
